**Contract (implementation note).**
- Outcomes per recipient × channel: `queued`, `sending`, `simulated`, `provider_accepted`, `delivered` (in-app feed row only), `failed`, `ambiguous`, `skipped`, `cancelled`, plus a short error code (never provider text). Push is "accepted" when any device ticket is accepted; Expo receipts are not polled, so push never reports `delivered`.
- One logical effect per action, unique per organization by `effect_key`: `assignments:<plan>:<key>`, `notify:<plan>:<key>`, `plan-changed:<plan>:<uuid>`, `assignment-response:<history id>`, `assignment-link-response:<link id>`. Clients send optional `idempotency_key` (8–200 chars) on create plan, duplicate, import, schedule and notify.
- Scheduler-update rule (both answer paths, one SQL function): every distinct `created_by` of the answered positions except the responder gets one in-app + push update; email only on decline/withdrawal. Dispatch re-checks that the scheduler is still an active owner/admin/scheduler (MOB-004 rule). Response scope unchanged: link still answers all of the person's answerable positions on the plan.
- Dispatch re-checks at send time: plan exists, recipient still an active member, positions still on the plan and not declined (reminders: still unconfirmed). Otherwise `cancelled`.
- Compatibility: `AssignmentNotificationSendResult` keeps `notified`/`skipped` and adds `effect_id`, `email_mode`, `outcomes`, `summary`. **`notified` now counts only provider-accepted emails** (simulated = 0). `notified_at`/`sent_at` are set only on provider acceptance. Link confirmations now also notify the scheduler in-app (consistency with the app path). Scheduling now requires the person to have an `organization_members` row in the plan's org.

### Policy (handoff)
- **Time mode.** `all` covers every time on the plan, including times added later; `selected` covers only the chosen ids and never acquires a new time silently. Links must be on the same plan (trigger + RPC checks).
- **Added time** joins `all` requests (shown as "gains" in the preview); **removed time** drops its selection links and its current per-time answers (history keeps the answer with a NULL time); a `selected` request left with no time must be resolved in the commit (`all` → rechecked for conflicts, or `remove`); **changed time** (start/end/kind) is material. Renames are not.
- **Untimed fallback.** A plan with no times resolves to one `untimed_fallback` interval (service date + 2 h), labelled everywhere (`source`, `untimed`, "Time not set" on web/native, "approximate" in conflicts). Plans without times still never reach the calendar/feed.
- **Conflicts.** Union of actual half-open intervals (rehearsal/other included). Kinds: `blockout` (always `blocking`, detail "Unavailable", reason never returned) and `overlapping_commitment` (`blocking` on another plan; `warning` for a second position on the same plan — shown, never ignored, not blocking). Excluded: only the assignment ids passed and the identical obligation (same plan/team/position). A commitment on a plan the caller cannot schedule or edit reads "Another commitment" with no plan/assignment id. Prepared requests count only for callers who can see them (F01). Preferences/freshness stay separate F03 warnings.
- **Override.** New capability `scheduling.override_conflicts` (org/folder/service type/team; owners, admins and legacy schedulers hold it). Needs a reason (1–500 chars); recorded per request in `assignment_conflict_overrides` with the redacted conflicts at that moment. Copies (duplicate/import/create-from) re-check like any writer and refuse unless an authorized reason is given.
- **Calendar.** UID stays `plan-time-<id>@host`; SEQUENCE = `plan_times.ics_sequence` + a per-Person `attendance_calendar_states.sequence_offset` bumped whenever that Person's applicability flips; a time a Person no longer attends is published as `STATUS:CANCELLED` in their feed. ### Rule and count definitions (rule version `f06.fairness.v1`)
- **Slots:** for each selected plan (by service date, id) × selected team need (by team id, position id) × `needed`. Existing non-declined requests on that plan/team/position fill slots first and are always kept (if more exist than needed, all are shown as kept). Declined requests do not fill.
- **Hard exclusions (never overridden):** not a member of that exact team position; blocking F04 conflict for an all-times request (`blockout`, or `overlapping_commitment` on another plan); already has any request on the plan (including declined); already proposed for that plan; excluded by the reviewer. Prepared requests count only when the author can see them (RLS).
- **Order of choice per slot:** existing → reviewer locks (an invalid lock leaves the slot open with `locked_choice_invalid`, never silently replaced) → team rotation person for that civil week/exception (if ineligible: `vacancy` policy leaves an explained vacancy; `fairness` policy falls through) → fairness.
- **Fairness:** people without F03 preference warnings first, then fewer distinct plans served in `[plan date − lookback, plan date)` (caller-visible, non-declined, any team, **including earlier choices of the same proposal**), then least recently served, then FNV-1a tie-break of `seed|plan|position|person`, then person id. Freshness codes (`availability_unknown`, `availability_stale`) are shown per choice but never change order or create warnings (QA finding: they applied to nearly everyone and flattened the tier). The policy text shown in the UI is generated from the same function (`describeProposalPolicy`).
- **Vacancy reasons:** `no_position_members`, `all_candidates_excluded` (with per-reason counts), `locked_choice_invalid`, `rotation_member_unavailable`, `rotation_member_missing`.
- **Rotations:** `cycle_weeks` 1–12; week index = `floor(civil days(anchor → plan local date) / 7) mod cycle` (dates before the anchor wrap); plan local date = service instant in the organization's IANA zone; civil-date arithmetic is DST-free. Exceptions per local date × position: a person, or skip (fairness decides). Missing people (left the position, archived, deleted → cascade) produce `rotation_member_missing`, never an assignment. ### Contract (implementation note)
- **Release batches** (`release_batches`/`release_batch_items`): exact reviewed `(assignment_id, request_revision)` pairs across any number of plans, `notify`, `scheduled_for`, idempotency key per creator (same key + different content → 409). `create_release_batch` releases in the same transaction (stale → PT409, nothing committed) or records it scheduled. `private.execute_release_batch` (also used by the worker) takes the per-plan `release:` advisory locks in plan order, row-locks assignments in id order, and fails the whole batch (`scope_changed`, `actor_not_permitted`) if any row changed, disappeared, or the creator lost membership/scheduling scope. One consolidated effect per batch (`delivery_effects.release_batch_id`, `plan_id` null when multi-plan), one snapshot per Person **per plan** (unique index now `(effect_id, person_id, plan_id)`), one delivery per Person per channel. The email lists each plan with its own link; a link answers only its plan's snapshot.
- **Link continuity** (`assignment_notifications.previous_token_hash/previous_snapshot_id/previous_expires_at/issued_delivery_id`, `issue_assignment_link`): a resend keeps the last provider-accepted token (and its snapshot) usable until the replacement is accepted (`complete_delivery` then clears it and supersedes the old snapshot). An unaccepted current token is simply replaced. Either token consumes the row, so one answer. With `DELIVERY_LINK_SECRET`, tokens are `HMAC(delivery, plan)` — identical on every retry of a delivery — and Resend gets `Idempotency-Key: delivery-<id>`; Resend's 409 `invalid_idempotent_request` is recorded as `ambiguous` (`provider_duplicate_key`).
- **Policies** (`reminder_policies`): kinds `pending_response` / `confirmed_service`; scope team → service type → organization → built-in default; `enabled`, `offset_minutes` (15 min–30 days), channels, quiet window (org time zone, may cross midnight), `max_per_day` (per Person per channel, rolling 24 h), `revision` (bumped by trigger; API `expected_revision` → 409). **Proposed Service Center defaults (not reference-product claims):** pending 72 h before the first applicable *service* time; confirmed 24 h before the first applicable *attendance* time (rehearsals count); all channels; no quiet hours; 2/day. Write access: org = admins; service type = `scheduling.manage` or `plans.edit` there; team = `scheduling.manage` or `teams.manage` on the team (RLS, mirrored by shared `canEditReminderScope`). `person_reminder_preferences`: each member opts channels out of reminders (requests unaffected).
- **Jobs** (`reminder_jobs`): semantic key `kind:person:plan:request_version:policy@revision:occurrence(time@epoch):channel`, unique per org; `request_version` = md5 of the sorted (assignment, request_revision, status) set, so one job covers all of a Person's positions on a plan per policy. Triggers queue plans (`reminder_recompute_queue`) on assignment/time/attendance/plan/policy/preference/archive/membership changes; the worker (and `plan_reminder_jobs` reads) recompute: new intents inserted, no-longer-desired `scheduled` jobs and `enqueued` jobs with unsent deliveries cancelled. A job first computed after its due time is recorded `skipped/due_passed` (no catch-up burst for brand-new requests); one that was scheduled but missed while the worker was down is still sent while the occurrence is in the future. `materialize_due_reminders` (SKIP LOCKED) re-checks desirability, quiet hours at send time (defer to the window end, skip if that passes the occurrence), the daily cap (defer to when the oldest drops out, else skip), then creates one effect (`reminder:<job>`, `assignment_reminder` or new `service_reminder` template) with one delivery; pending email reminders get their own exact snapshot/link. The dispatcher calls `reminder_job_is_current` before any provider call → `cancelled/reminder_obsolete` if the answer, removal, archive, time, policy, preference or membership changed after enqueue.
- **API:** `GET /releases/prepared`, `POST /releases/preview` (per Person → plans → requests with times, reachable/skipped channels), `POST /releases` (201 released / 202 scheduled), `GET /releases`, `POST /releases/:id/cancel`; `GET|PUT /reminder-policies` (`service_type_id`/`team_id` scope; effective + explicit + `can_edit`), `DELETE /reminder-policies/:id`, `GET|PUT /reminder-policies/me`; `GET /plans/:id/deliveries` (scheduled reminders + per-Person/channel history; retry flag for admins). Existing `/plans/:id/release` and `/plans/:id/notify` unchanged. Worker run result gains `releases`, `remindersEnqueued`.
- **Visibility:** new RLS lets a scheduler read delivery effects/deliveries for requests they schedule (ids and codes only; never addresses or content). Reminder jobs readable by admins and schedulers of the covered rows; queue and batch writes are function-only.
