**Contract (implementation note).**
- Outcomes per recipient × channel: `queued`, `sending`, `simulated`, `provider_accepted`, `delivered` (in-app feed row only), `failed`, `ambiguous`, `skipped`, `cancelled`, plus a short error code (never provider text). Push is "accepted" when any device ticket is accepted; Expo receipts are not polled, so push never reports `delivered`.
- One logical effect per action, unique per organization by `effect_key`: `assignments:<plan>:<key>`, `notify:<plan>:<key>`, `plan-changed:<plan>:<uuid>`, `assignment-response:<history id>`, `assignment-link-response:<link id>`. Clients send optional `idempotency_key` (8–200 chars) on create plan, duplicate, import, schedule and notify.
- Scheduler-update rule (both answer paths, one SQL function): every distinct `created_by` of the answered positions except the responder gets one in-app + push update; email only on decline/withdrawal. Dispatch re-checks that the scheduler is still an active owner/admin/scheduler (MOB-004 rule). Response scope unchanged: link still answers all of the person's answerable positions on the plan.
- Dispatch re-checks at send time: plan exists, recipient still an active member, positions still on the plan and not declined (reminders: still unconfirmed). Otherwise `cancelled`.
- Compatibility: `AssignmentNotificationSendResult` keeps `notified`/`skipped` and adds `effect_id`, `email_mode`, `outcomes`, `summary`. **`notified` now counts only provider-accepted emails** (simulated = 0). `notified_at`/`sent_at` are set only on provider acceptance. Link confirmations now also notify the scheduler in-app (consistency with the app path). Scheduling now requires the person to have an `organization_members` row in the plan's org.

Implicit access: owner/admin = every capability org-wide; scheduler = every capability org-wide while `organization_members.access_mode = 'legacy'` (default for all existing and new rows); member = explicit grants only. **Ceilings:** granting, membership, roles, access mode, folder structure and org settings are owner/admin only (`is_org_admin`); no capability authorizes them, so no grant at any scope can issue grants. Grants reference an active membership of the same org (composite FKs); removing a membership revokes its grants; capability/scope pairs are constrained (`access_grants_capability_scope`). **No explicit deny entries** — restriction is by scoping a scheduler and granting less. Medical note: owner/admin only (`person_medical_note`), not selectable by API roles at all. `can_manage_org` now means "holds some plans/scheduling/teams capability" and is only a coarse first gate; row policies decide scope. Effective access is one resolver (`private.capability_for`, folder-aware) used by RLS, Storage, invoker/definer functions, the worker and `my_effective_access` (sent with `/me` per membership and as `req.access`); the shared `canAccess` mirrors it for UI hints only.

### Policy (handoff)
- **Time mode.** `all` covers every time on the plan, including times added later; `selected` covers only the chosen ids and never acquires a new time silently. Links must be on the same plan (trigger + RPC checks).

### Rule and count definitions (rule version `f06.fairness.v1`)
- **Slots:** for each selected plan (by service date, id) × selected team need (by team id, position id) × `needed`. Existing non-declined requests on that plan/team/position fill slots first and are always kept (if more exist than needed, all are shown as kept). Declined requests do not fill.
