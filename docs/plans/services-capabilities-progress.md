**Contract (implementation note).**
- Outcomes per recipient × channel: `queued`, `sending`, `simulated`, `provider_accepted`, `delivered` (in-app feed row only), `failed`, `ambiguous`, `skipped`, `cancelled`, plus a short error code (never provider text). Push is "accepted" when any device ticket is accepted; Expo receipts are not polled, so push never reports `delivered`.
- One logical effect per action, unique per organization by `effect_key`: `assignments:<plan>:<key>`, `notify:<plan>:<key>`, `plan-changed:<plan>:<uuid>`, `assignment-response:<history id>`, `assignment-link-response:<link id>`. Clients send optional `idempotency_key` (8–200 chars) on create plan, duplicate, import, schedule and notify.
- Scheduler-update rule (both answer paths, one SQL function): every distinct `created_by` of the answered positions except the responder gets one in-app + push update; email only on decline/withdrawal. Dispatch re-checks that the scheduler is still an active owner/admin/scheduler (MOB-004 rule). Response scope unchanged: link still answers all of the person's answerable positions on the plan.
- Dispatch re-checks at send time: plan exists, recipient still an active member, positions still on the plan and not declined (reminders: still unconfirmed). Otherwise `cancelled`.
- Compatibility: `AssignmentNotificationSendResult` keeps `notified`/`skipped` and adds `effect_id`, `email_mode`, `outcomes`, `summary`. **`notified` now counts only provider-accepted emails** (simulated = 0). `notified_at`/`sent_at` are set only on provider acceptance. Link confirmations now also notify the scheduler in-app (consistency with the app path). Scheduling now requires the person to have an `organization_members` row in the plan's org.

### Policy (handoff)
- **Time mode.** `all` covers every time on the plan, including times added later; `selected` covers only the chosen ids and never acquires a new time silently. Links must be on the same plan (trigger + RPC checks).
- **Added time** joins `all` requests (shown as "gains" in the preview); **removed time** drops its selection links and its current per-time answers (history keeps the answer with a NULL time); a `selected` request left with no time must be resolved in the commit (`all` → rechecked for conflicts, or `remove`); **changed time** (start/end/kind) is material. Renames are not.
- **Untimed fallback.** A plan with no times resolves to one `untimed_fallback` interval (service date + 2 h), labelled everywhere (`source`, `untimed`, "Time not set" on web/native, "approximate" in conflicts). Plans without times still never reach the calendar/feed.
- **Conflicts.** Union of actual half-open intervals (rehearsal/other included). Kinds: `blockout` (always `blocking`, detail "Unavailable", reason never returned) and `overlapping_commitment` (`blocking` on another plan; `warning` for a second position on the same plan — shown, never ignored, not blocking). Excluded: only the assignment ids passed and the identical obligation (same plan/team/position). A commitment on a plan the caller cannot schedule or edit reads "Another commitment" with no plan/assignment id. Prepared requests count only for callers who can see them (F01). Preferences/freshness stay separate F03 warnings.
- **Override.** New capability `scheduling.override_conflicts` (org/folder/service type/team; owners, admins and legacy schedulers hold it). Needs a reason (1–500 chars); recorded per request in `assignment_conflict_overrides` with the redacted conflicts at that moment. Copies (duplicate/import/create-from) re-check like any writer and refuse unless an authorized reason is given.
- **Calendar.** UID stays `plan-time-<id>@host`; SEQUENCE = `plan_times.ics_sequence` + a per-Person `attendance_calendar_states.sequence_offset` bumped whenever that Person's applicability flips; a time a Person no longer attends is published as `STATUS:CANCELLED` in their feed. Email invites use the same sequence. Existing feed tokens and UIDs are unchanged.
