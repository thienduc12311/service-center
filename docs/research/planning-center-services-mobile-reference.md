# Planning Center Services Mobile reference

Research date / all sources accessed: **2026-10-15**. Starting point: [Services Mobile](https://help.planningcenter.com/en/143018-services-mobile.html). Scope is the native Services iOS/Android product, including explicitly labeled mobile procedures in shared Services articles. This supplements [the Services reference](planning-center-services-feature-reference.md); it does not assume that every website feature exists on mobile.

The supplied category rendered only a heading to the text parser. Official mobile articles were recovered through the Services overview, article links, and targeted searches of `help.planningcenter.com`. Public documentation describes intended behavior; no authenticated Planning Center account, device build, provider contract, or API implementation was tested. M01–M39 below are stable source IDs for the mobile plan/spec. All capability summaries are original paraphrases.

## Scope boundaries for service-center planning

1. **Do not turn every web gap into a mobile parity task.** Copy-plan, temporary-position creation, general/household preferences, recurring-series edits/deletes, whole-order clearing, and date-range plan browsing have documented web limitations above. Supporting them natively in service-center is an intentional extension.
2. **A browser launch is not native implementation.** Music Stand is a separate optional product/app. Ordinary Services Mobile PDF viewing does not establish annotation, pedal controls, synchronized page turns, or Music Stand's full offline behavior. [M36](#m36), [M37](#m37)
3. **Songbook generation is web-only in the comparison table.** Services Mobile downloads rehearsal audio and opens documents; it does not document generating a combined PDF songbook. A service-center native songbook task must be labeled an extension. [M36](#m36)
4. **Auto-scheduling and new-person creation remain unverified on mobile.** The reviewed auto-schedule and person-import articles describe website procedures; do not cite them as native mobile functionality. Shared backend support can still justify service-center tasks. Multi-plan matrix, stage-layout authoring, custom-report authoring, and full organization settings likewise need separate mobile evidence before parity claims. [M38](#m38), [M39](#m39)
5. **Do not infer offline writes from caching.** Documentation supports temporary rehearsal-audio downloads and cache management, not generalized offline editing, durable local mutation queues, or cross-account offline access. Such requirements are service-center design decisions. [M22](#m22), [M23](#m23)
6. **Feature availability and implementation are separate.** File authorization, leadership scope, current membership, provider entitlements, OS capabilities, push credentials, and physical-device behavior must be validated in the service-center implementation. Help text does not establish the reference product's API contract or data model.
7. **Visual consistency is the user's service-center requirement.** These sources establish mobile workflows, not a requirement to copy Planning Center's branding or adopt an editorial/minimalist style. Shared service-center website/mobile design tokens and semantic statuses should be specified against repository evidence.
