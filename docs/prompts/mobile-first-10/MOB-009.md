# MOB-009 — Eligible openings, signup and approval

Read [the common instructions](README.md) first. Execute the backend pass before native integration. Requires MOB-005's Person/access/attendance/release contracts; reuse MOB-008's plan staffing/count semantics. F07 opportunities and atomic capacity are new shared capabilities, not existing mobile APIs.

**User story:** As an eligible volunteer, I see open positions and required times, review an opening and claim it once, knowing whether my place is confirmed or awaiting approval.

**Read:** mobile specification staffing/opportunities section; Services F07 and F04; US-07.1; current assignment, plan-needs and team membership storage/routes; shared API/domain/schemas; native schedule and plan screen; scoped authorization and outbox from MOB-005. Read the database skill's schema, RLS and locking references before design.

## Pass A — Opportunity policy and atomic allocation

1. Define shared DTOs for an opportunity, eligibility result, signup preview, claim, approval action and capacity result. An opportunity references a real organization, plan, team/position and attendance scope, with capacity, closing time and direct-versus-leader-approval policy. Use server time and explicit versions. Initial access is authenticated eligible Persons; public account signup and household delegation are outside this task. **Done:** contract examples distinguish eligible/full/closed/unavailable and confirmed/awaiting-approval states.
2. Record the initial state machine before coding: a direct approved-policy claim creates a confirmed assignment based on the claimant's explicit consent; an approval-policy claim creates a capacity reservation awaiting authorized leader approval, then creates/finalizes the assignment. Rejected/cancelled/expired reservations release capacity. Pending claims need a bounded expiry policy, visible to the user. A retry returns the same existing claim rather than a second one. **Done:** every transition has actor, expected state/version, capacity effect and persisted history.
3. Add additive tables/constraints/indexes and RLS for opportunities/claims/reservations. Validate organization and all plan/team/position/time relationships, uniqueness of the Person's active claim and idempotency keys. Explicitly opening an opportunity exposes only its reviewed audience/scope; it does not grant full-plan access or reveal prepared assignments through counts. Keep claimants' contact/private conflict data out of the opening list. **Done:** direct SQL tests deny another Person's claim, foreign team access and forged parent/time relationships, and opening details reveal no private preparation.
4. Implement one canonical transactional capacity operation used by signup, leader approval and later replacements. Lock a stable resource broad enough to serialize overlapping time scopes, such as plan/position, then calculate occupancy per applicable time. Include occupying assignments and active reservations; declined/cancelled/expired rows do not count. Explicitly define capacity versus plan needs so the two cannot advertise contradictory open slots. Expire due reservations inside allocation before counting; add bounded cleanup using the existing dispatcher if needed. **Done:** one final slot produces exactly one successful allocation across concurrent transactions.
5. Route all competing assignment writers through the same allocation/check boundary, including manual scheduling, status changes, selected-time changes and needs/capacity changes. An explicitly permitted manual overstaff override must be audited, close signup availability and never let a volunteer bypass capacity. Revalidate eligibility, conflicts, deadline and opportunity/time revisions inside the transaction. External email/push occurs only from committed outbox work. **Done:** signup versus manual scheduling and overlapping-time claims cannot both consume the same final capacity through different endpoints.
6. Implement minimal typed API operations in existing route conventions: list eligible opportunities, detail/preview, idempotent claim, own cancellation and authorized approve/reject. Suggested resource names are `/signup-opportunities` and nested `/claims`; they are new contracts to implement, not endpoints already available. Add leader setup/approval controls at the existing plan Teams entry point so opportunities can be created and managed without seed-only/admin-console steps. **Done:** the feature can be exercised end to end by actual permitted users in a local fixture.
7. Write integration tests with two independent database connections/transactions, synchronized to contend for the same final slot. Cover direct claim, approval reservation, cancellation/expiry, duplicate retry, duplicate Person claim, deadline, membership revoked after preview, changed times and signup versus manual fill. Assert final rows/occupancy and outbox uniqueness, not only HTTP responses. **Done:** tests prove database atomicity and rollback behavior with real contention.

## Pass B — Native opportunities and claim review

8. Add an “Open positions” entry from My Schedule or the existing plan Teams area using shared primitives. Use bounded pagination, organization/team/service filters supported by the API, and explicit empty/full/closed/error states. Show required service/rehearsal times, position, remaining capacity, closing time and approval policy. **Done:** users discover only eligible openings without downloading the full private roster.
9. Add review and explicit Claim. Submit the previewed version with a stable idempotency key retained for retries. Pending/timeout states must refresh the existing claim before offering another submit. Display confirmed versus awaiting approval distinctly and provide permitted cancellation. Server stale/full/closed results refresh details while preserving understandable context. **Done:** neither a timeout nor offline action is displayed as a committed slot without server confirmation.
10. Add leader approval status/actions using the same capability and transaction contract; refresh schedule, plan counts and opportunities after success. Test last-slot loss, revoked eligibility, expiry, cancellation and organization switch in the native flow. Run common checks and record device gates. **Done:** native and website/API reloads show the same claim, assignment and capacity.

## Acceptance checks

- Only currently eligible Persons can claim the exact offered attendance scope before closing.
- One last slot is allocated once under signup/signup, signup/manual and approval/replacement contention once MOB-010 is added.
- Approval reservations have visible state and finite lifecycle; cancelling, rejecting or expiring them restores capacity once.
- Delivery failure does not undo a committed claim or create duplicates on retry.
- The UI accurately distinguishes review, submitting, awaiting approval, confirmed, full, closed and failure; all authorization checks are server enforced.

**Handoff:** describe resource contracts, state machine, expiry/capacity policy, all assignment writers integrated and actual concurrency evidence. MOB-010 must reuse this allocator rather than adding its own check-and-insert.
