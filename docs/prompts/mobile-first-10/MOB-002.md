# MOB-002 — Preserve plan-specific chart context

Read [the common instructions](README.md) first.

**User story:** As a scheduled musician, I open a song from a plan and see that item's chosen arrangement, service key and sequence. When browsing the song library, I can choose an arrangement without changing another plan.

**Read:** mobile specification MOB-002; US-11.2; `mobile/app/plan/[id].tsx`; `mobile/app/song/[id].tsx`; `mobile/src/components/ChordChart.tsx`; shared `types/domain.ts`, `types/database.ts`, `schemas/plan.ts`, `schemas/song.ts`, `lib/chordpro.ts`, its tests and `lib/api-client.ts`; backend song/plan routes and services; website `frontend/src/components/song/ArrangementPanel.tsx` and plan order components as behavior references.

**Baseline to verify:** plan navigation currently passes only the song ID; the song screen chooses a default arrangement and ignores the item's key override. Plan items reference an arrangement and key, while the selected arrangement already has a sequence. A persisted per-item sequence override is not currently a complete shared capability.

## Pass A — Correct context and arrangement selection

1. Trace the actual plan-item and arrangement shapes. Define a small typed chart-context resolver with explicit precedence: use the referenced plan-item arrangement; use the documented song default/fallback only when no arrangement was explicitly selected or when browsing the library. An explicitly referenced but missing/invalid arrangement shows unavailable rather than substituting another version. The displayed service key comes from the item override when present, otherwise the selected arrangement/song source key. **Done:** the resolver's input/output describes source key, display key, selected arrangement and effective sequence without duplicating shared boundary types.
2. Pass plan ID and item ID when opening a chart from a plan. Re-fetch authorized plan/song data; resolve the item by ID and confirm its song and arrangement relationships. Treat URL values as untrusted. Show loading until context is resolved; show unavailable/denied when invalid, rather than briefly showing a different chart. Namespace queries by session/organization using MOB-003's conventions if already present. **Done:** a valid item selects its actual arrangement and a forged/mismatched item cannot supply chart context.
3. Feed the effective key into the shared transposition pipeline exactly once. Use the same result for chart chords and key label. Reset local transpose, notation/arrangement overrides as appropriate when song, item or organization changes. Missing/unsupported source keys must produce a clear unavailable transposition state rather than incorrect chords. **Done:** opening a C-source arrangement in a D service key shows D in both chords and heading, with subsequent semitone adjustments applied once.
4. Add an accessible arrangement picker for library browsing. In plan context, show the plan's selected arrangement and label temporary viewing changes; viewing an alternative never saves back to the item or song automatically. Explicitly distinguish a local display change from plan editing, which belongs to MOB-014. **Done:** library selection and plan-specific context remain independent when navigating between screens.
5. Add focused resolver/rendering tests covering a nondefault arrangement, key override, missing/deleted arrangement, invalid item/song relationship and state reset boundary. Manually inspect picker and chart scrolling on the native screen. **Done:** tests assert actual chord/key/sequence output, and common native checks pass.

## Pass B — Persisted per-item sequence override

6. Recheck whether an earlier change has supplied the sequence override. If absent, read the database skill, then add the smallest compatible nullable item-level sequence contract and migration. Null inherits the arrangement sequence; an explicit valid sequence overrides only that item. Validate section references using the same rules as arrangement sequences. Preserve existing website item updates and historical items. **Done:** shared types, validation, API read/write and storage agree, with migration/RLS coverage.
7. Wire the resolver to this persisted field. Expose only the minimal existing item-editing compatibility needed to save/read the contract; a full native order editor is outside this task. Test two plan items using the same song with different sequences and keys, and null inheritance. **Done:** changing one item's persisted sequence cannot alter the arrangement or the other plan.

## Acceptance checks

- Plan item A uses arrangement B in D even if the song default is arrangement A in C.
- Opening the same song from another plan or the library restores that context's own key/sequence.
- Invalid plan/item/song/arrangement combinations fail safely; no unauthorized chart or stale prior organization content appears.
- Empty charts, missing key and deleted resources have explicit states; controls remain usable in both themes.
- Pass A can be recorded separately, but the full task remains partial until persisted per-item sequence behavior in Pass B is implemented and verified.

**Handoff:** name the pass completed and remaining sequence/device gates. Next independent task: MOB-003.
