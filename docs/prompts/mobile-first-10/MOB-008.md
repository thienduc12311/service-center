# MOB-008 — Edit plan needs and schedule eligible candidates

Read [the common instructions](README.md) first. Use MOB-005's scoped Person/time/release contracts and MOB-007 warnings. Existing Profile-only staffing can be an intermediate pass, but no-login acceptance requires the completed identity foundation.

**User story:** As an authorized leader, I see staffing needs by position, inspect suitable people and their conflicts, and prepare or release an assignment deliberately from my phone.

**Read:** mobile specification staffing section; Services F01/F02/F04/F08; native plan screen; website `frontend/src/components/plan/TeamsTab.tsx`, `SchedulePeopleModal.tsx`, `types.ts`; backend team/people/assignment/plan routes; shared needs, assignment, conflict, people, team and API contracts.

## Pass A — Plan Teams view and staffing needs

1. Trace the existing needs endpoint and website grouping logic. Define a reusable pure view model where needed; native must consume shared/backend contracts rather than importing website components. Add an Order/Teams switch or Teams section within the current native plan screen. A full Plans navigation browser is MOB-012. **Done:** the current plan can show all permitted teams, positions and their stable IDs without new unrelated navigation.
2. Show requested headcount, confirmed, pending/prepared/released where authorized, declined and genuinely open counts per position. Define how pending requests count toward staffing versus confirmed totals; declined rows do not fill a vacancy. Preserve multiple positions and selected-time scope. Use the canonical allocator once MOB-009 exists. **Done:** test fixtures with mixed answers/multiple times produce the same counts as the server and website.
3. Add plus/minus need controls using the existing `setPlanPositionNeeds` contract, with bounded nonnegative values, stale-write review and correct PATCH semantics. Preserve omitted positions instead of zeroing them accidentally. Gate editing by capability and enforce parent/team/position/org relationships server-side too. **Done:** simultaneous changes cannot silently overwrite newer needs or modify an unauthorized team.

## Pass B — Candidate preview and scheduling commit

4. Build a bounded/searchable candidate picker using existing roster/team/position APIs, adding a minimal candidate-preview contract if these cannot safely return all needed information. Show recent serving, applicable times, redacted conflicts and preferences. Enforce actual position/team eligibility; allow an existing roster Person as a plan-only guest only through an explicit authorized choice. Creating a new Person or temporary position is outside initial native parity. **Done:** an unrelated roster entry is not presented as a qualified member, and no-login Persons are usable only after the shared migration supports them.
5. Preview exact Person, position, times, conflict/warning results, preparation/release choice and recipient/delivery readiness. For a permitted hard-conflict override, require an explicit action and reason persisted to audit. The current naked `ignore_conflicts` boolean is insufficient; extend the shared schema/service if necessary. **Done:** the user understands what will be saved and who will see/receive it before confirmation.
6. Commit through an idempotent, authorized server operation that rechecks eligibility, conflicts, revisions and resource relationships. Honor all/selected attendance times and the exact prepare/release choice. Keep conflict/version checks and assignment creation consistent under concurrent commits; serialize the relevant Person/time scheduling changes where required. Reuse MOB-005's outbox, not another notification sender. **Done:** a change between preview and commit produces a refreshed conflict/stale result instead of an unreviewed assignment.
7. Display saved preparation/release state and truthful delivery outcomes; “saved” and “provider accepted” are distinct. The existing create endpoint's created/conflicts response may need expansion to expose these results. Keep selection/draft on recoverable failure and refresh only the active plan/organization queries after success. **Done:** missing email/provider errors never appear as successful delivery, and retry creates no duplicate assignment.

## Acceptance checks

- Authorized leaders edit only their permitted positions; members and leaders of another team cannot bypass controls through direct requests or RLS.
- Needed/confirmed/pending/declined/open counts remain correct across multiple positions, withdrawals and time subsets.
- A blockout/rehearsal collision is rechecked at commit; an override requires permission, reason and audit.
- Linked and no-login Persons can be scheduled once the identity prerequisite is available; adding a guest does not silently add permanent team membership.
- Preparing sends/shows nothing to the recipient; explicit release follows the shared visibility/notification contract.
- Tests cover retry/deduplication, wrong plan/team/position relationships, concurrent stale needs and conflicting scheduling commits. Common checks and native interaction review pass.

**Handoff:** record completed pass, permission rules, count semantics and commit/transport checks. Leave the full task partial if only Profile-only or unversioned staffing works. Next task: MOB-009.
