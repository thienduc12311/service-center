# MOB-003 — Isolate sessions and organizations; validate links

Read [the common instructions](README.md) first. Work in three passes so each security boundary can be verified independently.

**User story:** As someone using multiple organizations or a shared device, I only see my active authorized data. Invitations and assignment responses open correctly, including a public response without an account.

**Read:** mobile specification MOB-003; shared F00/F02/F08 sections as needed; ADR 0001; `mobile/src/providers/AuthProvider.tsx`, `NotificationsProvider.tsx`; `mobile/src/lib/api.ts`, `notification-keys.ts`, `push.ts`; `mobile/app/_layout.tsx`, `accept-invite.tsx`, `notifications.tsx`, `songbooks/[id].tsx`; `mobile/app.config.js`; website `RespondAssignmentPage.tsx` and deployed association-file configuration; shared API client/schemas; backend `assignment-respond.ts`, notification routes/model and auth middleware.

## Pass A — Query and session lifecycle

1. Inventory every native query key, mutation callback and persisted organization value. Identify which data is account-wide versus organization-scoped. The songbook detail key currently lacks organization scope. **Done:** all sensitive caches and asynchronous writers are accounted for, with exact call sites.
2. Introduce/reuse typed key factories scoped by authenticated user and organization where applicable. Enable protected queries only after session and organization hydration/validation completes. Make each request use an immutable identity/org context for its lifetime; mutable global organization reads during a switch must not combine one user's token with another context. Preserve existing website client compatibility if extending the shared client. **Done:** new requests and cached results have one unambiguous identity/tenant.
3. Implement a transition sequence: hide old protected content, advance a session generation, cancel relevant in-flight queries, clear old account/tenant data, validate the next organization, then enable its queries. Ignore late loads/callbacks from an older generation. Clear sensitive local UI state and query/mutation caches on sign-out. Stale unauthorized responses may not sign out a newer session. **Done:** slow responses from A cannot populate B or replace its organization after a switch/sign-out.

## Pass B — Device registration lifecycle

4. Trace push registration ownership and sign-out order. Currently unregister is attempted after authentication is gone, and failure is swallowed. Unregister while the captured session still has authority, bound waiting so sign-out cannot hang, and guard late registration results. Ordinary organization switching must retain the user's account-wide device registration. Reset badges/client state on sign-out. **Done:** successful sign-out unregisters the old association and late registration cannot restore it.
5. Handle offline/expired-session cleanup at the server boundary as necessary: use revocable/expiring session-bound registration authorization or an equivalent verified mechanism so a stale row is not treated as safely active forever. Inspect actual Supabase/session capabilities before choosing a design; read the database skill before changing persistence. Specify online revocation versus offline lease expiry honestly: a server cannot instantly learn about an offline local sign-out. Minimize lock-screen payloads and never rely on client navigation checks to prevent private OS delivery. **Done:** tests prove exclusion after server revocation/expiry; the remaining offline interval and already delivered OS notifications are documented as limitations, not claimed to be instantly revoked.

## Pass C — Validated navigation and public responses

6. Parse external notification/link payloads from `unknown` using shared validation. Accept only configured hosts/schemes, supported routes, valid IDs and current resource authorization. Reuse the existing push fields (`organization_id`, `plan_id`, notification ID/type); do not invent chat targets. For a different organization, verify membership before switching. Deleted/forbidden/stale targets fall back to a safe screen with an explanation. Keep one validated private intent through login and consume it once. **Done:** cold start and foreground taps behave consistently without open redirects or arbitrary routing.
7. Add a public native `/respond` route using the existing public token API, without forcing login or returning a full plan. Mirror pending, success, invalid, expired, used and network-error states. Keep the token in transient memory only. The current endpoint groups Person/plan assignments and is not yet a snapshot/atomic implementation; label its scope truthfully and reuse MOB-005 once available. Preserve invitation behavior. **Done:** a signed-out person can view the minimal authorized request and submit its displayed scope, with token replay handled by the API.
8. Update native deep-link intent configuration and existing website association files for actual configured production hosts and `/respond` alongside invitations. Association deployment, signing and installed-device verification remain explicit gates when unavailable. **Done:** code/config is consistent; the report distinguishes local route tests from verified universal/app links.

## Acceptance checks

Test A→B organization switches while queries/mutations are delayed; sign-out then another account signing in; storage hydration racing `/me`; token refresh; invalid stored organization; stale unauthorized callback; late push registration; unregister failure; and duplicate push taps. Assert both cache contents and rendered gating, not only key strings.

Test malformed payloads, unauthorized organization, nonexistent plan, unknown host, public response without login, expired/used token and a private link resumed once after login. Keep raw credentials out of test output. Add meaningful lifecycle tests with controlled asynchronous completion; use shared/backend tests plus a minimal native harness only where necessary.

**Handoff:** record each pass separately. Strict sign-out delivery guarantees remain pending if server revocation cannot yet be proven. Next independent task: MOB-004; response-version/atomic upgrades continue in MOB-005.
