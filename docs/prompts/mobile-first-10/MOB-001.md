# MOB-001 — Verify the shared website/mobile visual system

Read [the common instructions](README.md) first. This task's theme implementation already exists in the working tree. Preserve it and finish verification or fix specific discrepancies. Do not rebuild the application around another design aesthetic.

**User story:** As a volunteer switching between the website and phone, I recognize the same brand, labels, actions and assignment statuses while retaining comfortable native controls.

**Read:** mobile specification §3; backlog MC09; `packages/shared/src/lib/design-tokens.ts`; `packages/shared/src/index.ts`; `frontend/src/lib/design-tokens.ts`; `frontend/src/index.css`; `frontend/src/components/ui.tsx`; `mobile/src/lib/theme.ts`; `mobile/src/components/ui.tsx`; `mobile/src/components/motion.tsx`; `mobile/app/_layout.tsx`; `mobile/app/(tabs)/_layout.tsx`; `mobile/app/(auth)/login.tsx`; `mobile/app.config.js`; mobile dependency manifest.

## Steps

1. Inventory the current token/adaptor paths. Trace primary/pressed colors, page/card surfaces, borders, text, semantic assignment statuses and radii from shared tokens into both clients. Verify that both schemes actually consume them. **Done:** a short table in the progress note identifies each role and its web/native consumer; any hardcoded conflicts have exact file locations.
2. Review typography, decoration and motion. The intended UI uses system sans-serif text, indigo actions and slate surfaces; chart-specific monospace remains valid. Confirm custom serif packages, ruled backgrounds and mandatory staggered entry motion remain removed. Keep existing component APIs unless a real defect requires changing them. **Done:** relevant screens use the shared primitives and have no dependency on removed editorial fonts.
3. Inspect schedule, calendar, songs, song detail, songbooks, plan detail, profile, notifications, login and invitation screens. Compare terminology and status meaning with the corresponding website surface. Check disabled/pending states, touch targets, safe areas, keyboard and bottom navigation. Fix demonstrated inconsistencies through the shared adapter or primitive where possible. **Done:** each observed discrepancy has either a targeted fix or a documented reproducible remaining issue.
4. Run available visual checks using the existing app/browser or native tooling. Record platform, viewport/device, theme, text scale and screen for each observation. Cover small phone, larger phone/tablet, light/dark, large text and keyboard-visible forms. Use actual screenshots when the environment supports them; unavailable physical-device checks remain pending. **Done:** the visual matrix names tested cases and untested cases separately.
5. Run common typecheck/build/native export checks relevant to any changes. Behavioral tests are needed only if a fix changes behavior; avoid tests that merely copy color constants. Review the diff for accidental navigation or feature removals. **Done:** checks and remaining device gates are recorded without treating compilation as visual verification.

## Acceptance checks

- Both clients derive brand/status/radius roles from the shared source; confirmed, pending and declined remain distinguishable by text as well as color.
- No removed font dependency is imported, and UI remains legible with increased text size.
- Navigation labels and primary actions match the website vocabulary while native controls remain usable.
- All modified screens bundle for iOS and Android. Real device review remains a release gate until performed.
