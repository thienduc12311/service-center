# MOB-006 — Edit timezone-safe availability and create recurrence

Read [the common instructions](README.md) first. Implement one pass per invocation. Basic one-off editing can precede MOB-005; complete the identity/time integration before claiming the full conflict gate.

**User story:** As a volunteer, I enter all-day or timed unavailability in the organization's timezone, repeat it with a clear end, and see affected commitments without automatically declining them.

**Read:** mobile specification MOB-006/MOB-007; Services F03/F04; US-03.1 and US-04.2; `mobile/src/components/BlockoutForm.tsx`; native calendar/profile tabs; backend `blockouts.ts`, calendar/conflict routes and SQL RPC; shared blockout schema, database/domain/API types and `lib/dates.ts`; website blockout controls in calendar/settings pages.

**Baseline to verify:** existing blockouts store timestamp ranges against user IDs and support create/delete, not the complete update/recurrence workflow. Existing date helpers use device-local time; they are not an IANA organization-timezone conversion layer. The website does not yet supply a complete recurrence-maintenance handoff.

## Pass A — One-off contract and timezone conversion

1. Define timed versus all-day input semantics in shared contracts. All-day input stores date intent and timezone, resolving to an exclusive following local midnight; timed input displays the organization's IANA zone and preserves intended local time. Preserve existing one-off timestamp rows and use MOB-005's Person identity if available. **Done:** shared tests cover a device in another timezone and 23/25-hour DST days without changing the intended date.
2. Read the database skill, add compatible persistence/update contracts, and implement authorized one-off PATCH plus affected-assignment preview. Validate start before end, valid zone, sane bounded ranges and expected version. Define handling for nonexistent and ambiguous DST wall times: reject nonexistent times with a clear correction; require an explicit offset choice for an ambiguous time. **Done:** server validation agrees with client validation and stale edits cannot overwrite a later change.
3. Reuse one shared timezone/conversion implementation rather than duplicating web/native logic. Inspect existing dependencies; if a new package is needed, verify current official documentation and Expo/runtime compatibility before adding it. Use absolute timestamps only after resolving local intent. **Done:** UI, conflicts and persisted intervals round-trip through the same tested rules.

## Pass B — Bounded recurring series

4. Add a weekly/monthly series model with interval and an explicit until-date or occurrence-count end condition, plus exceptions for maintenance. Use bounded occurrence queries/expansion and idempotent creation. Define monthly missing-date handling explicitly in validation and preview rather than allowing JavaScript date overflow. Series IDs, occurrence IDs and revisions must support later edits without duplicating rows. **Done:** saving a long series does not materialize an unbounded future, and replaying creation creates one series.
5. Add preview and commit APIs using the same recurrence resolver. Recheck permissions and expected version at commit. Preserve local wall time/date across DST and redact private reasons from generic conflict output. **Done:** displayed next occurrences match the saved/queryable occurrences, including DST and end-condition boundaries.
6. Supply authorized web maintenance for one occurrence, this-and-future or the whole series, including delete and stale-version review, using existing website routing/components. This small web prerequisite is necessary because native parity hands existing-series maintenance to the website. Native should open that actual route; an unrelated settings link is not an implemented handoff. **Done:** a real route can load and maintain the exact selected series under the current user's permissions.

## Pass C — Native forms and conflict review

7. Replace raw date-text fields with native date/time inputs, all-day toggle, explicit zone label, recurrence frequency/end controls and occurrence preview. Verify any picker dependency against the installed Expo version. Initialize edits from server intent, retain draft on error and disable duplicate saves. Keep the native series view read-only with “Manage series on website”; one-off edit/delete remains native. **Done:** the same inputs render correctly after reopening in another device timezone.
8. Show affected existing assignments using the canonical attendance resolver from MOB-005, including rehearsals and split times. Apply the same audience rules: a volunteer's preview excludes prepared requests, while a scoped leader may see permitted preparation. A saved blockout never silently changes an answer. Offer a separate deliberate decline review through MOB-004/005's response contract. If preview and commit race, show refreshed affected commitments. **Done:** assignments stay unchanged until a distinct authorized response succeeds, and the preview leaks no private preparation.
9. Add tests for one-off update ownership, foreign Person/organization, invalid zone/range, DST spring/fall, monthly boundaries, finite expansion, recurrence exceptions, retry, stale edits and affected-assignment privacy. Run SQL/RLS checks for new persistence and the common shared/backend/web/native checks. **Done:** evidence covers actual stored intervals, not only formatted date labels.

## Acceptance checks

- An all-day Sunday blockout remains that local Sunday when the device timezone changes; its interval spans 23 or 25 hours on the relevant DST date.
- Create/edit/delete one-off, create/preview recurrence, end condition and website series-maintenance handoff work against persisted contracts.
- Rehearsal/service overlaps are identified from actual assigned times, and private reasons remain scoped.
- Existing commitments are not auto-declined; network failure retains form data and never displays a false saved state.
