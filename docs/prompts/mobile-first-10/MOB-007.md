# MOB-007 — Persist team scheduling preferences

Read [the common instructions](README.md) first. Depends on MOB-005's Person/access/time foundations; reuse MOB-006's organization-timezone semantics. Preferences have no complete persistence/API today.

**User story:** As a team member, I tell leaders how often and which weeks/times I prefer to serve, while my global blockouts remain clear hard unavailability.

**Read:** mobile specification availability/preferences section; Services F03/F04; US-03.2; shared people/team/domain schemas and types; backend people/team/conflict routes; native profile and plan screens; website team/member forms for vocabulary and membership behavior.

## Steps

1. Trace canonical Person→team membership and applicable service-time information. Define a shared preference DTO with optional serving frequency, monthly maximum, preferred/avoided weeks and selected attendance preferences, scoped to one Person/team/organization. Use stable recurring time categories or selectors when needed, not arbitrary IDs from last Sunday's plan. **Done:** every saved field has a definition, allowed values, unset meaning and a way to map it to a future dated plan.
2. Resolve unspecified details in a short implementation note before coding: frequency units; allowed maximum range; whether zero means no service or is rejected; week-of-month numbering and “last week”; overlapping preferred/avoided choices; treatment of split service times. Reuse an established contract if present; otherwise choose the smallest explicit options and use the same validation and help text everywhere. Count distinct served plans per organization-local month for frequency warnings so two positions on one plan do not double count. **Done:** no numeric value or week choice has an ambiguous interpretation.
3. Read the database skill. Add preference persistence with unique Person/team scope, same-organization relationships, version/timestamps and authorization. Implement typed GET and save under `/people/:id/scheduling-preferences`, matching the Services spec and existing routing style. Self edits require the linked Person; scoped leaders may access only the fields their capability allows. Household delegation is MOB-011 and must not be inferred from a relationship or query parameter. **Done:** SQL/API tests deny foreign Person/team access and reject invalid values.
4. Extend the canonical scheduling evaluation to return typed preference warnings separately from hard blockout/overlapping-commitment conflicts. Apply monthly counts, week and selected-time preference using the organization's local date. Warnings do not silently become hard exclusions or mutate existing assignments. Redact detailed personal information outside permitted leadership scope. **Done:** tests distinguish a preferred-time mismatch from a blockout and avoid double counting positions/times.
5. Add a “Team scheduling preferences” entry in native profile/settings, listing the current Person's authorized teams. Load/edit/save one team's preferences with explicit unset/default states and a short explanation of warning versus unavailable. Support loading, empty membership, validation, stale edit, pending and retry states. Preserve unsaved input on a failed save. **Done:** reopening the screen shows persisted values; changing organization clears the prior form.
6. Integrate display into the candidate/conflict review used by MOB-008 when available; otherwise provide the typed service result and focused tests for that later consumer. Keep global blockouts in a separate section. General preferences and household editing remain outside this task. **Done:** a leader can understand a permitted warning without seeing a private blockout reason.
7. Run shared validation/resolver tests, backend permission/round-trip tests, relevant RLS checks and common native checks. Include two teams with different preferences for the same Person, another organization, month boundaries and DST-local dates. **Done:** one team's update cannot overwrite another team's preference or leak across organizations.

## Acceptance checks

- Frequency, maximum, preferred/avoided weeks and service-time preferences persist and validate consistently.
- A user edits only their permitted Person/team scope; direct unauthorized API and SQL attempts fail.
- Warnings are separate from hard unavailability; current answers and global blockouts remain unchanged.
- Multiple positions on one dated plan count as one served plan for the stated monthly policy.
- Loading/error/stale states and both themes work; device-only checks are recorded honestly.

**Handoff:** document chosen preference semantics, schema/API, warning behavior and exact tests. Next task: MOB-008.
