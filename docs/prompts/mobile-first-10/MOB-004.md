# MOB-004 — Show the complete personal schedule and response actions

Read [the common instructions](README.md) first.

**User story:** As a volunteer serving in multiple positions on one plan, I see every responsibility and attendance time together, can filter my schedule, and can explain a decline or deliberately withdraw a confirmation.

**Read:** mobile specification MOB-004/MOB-005; `mobile/app/(tabs)/index.tsx`, `mobile/app/plan/[id].tsx`; shared `MyScheduleEntry` and related domain types, assignment schemas and API methods; backend `assignments.ts` and notification service; website schedule/assignment response behavior. Read ADR 0001 if changing grouped response scope.

**Baseline to verify:** schedule data already includes assignment, plan, team, position and times. Native cards are per assignment; the plan screen finds only the first personal assignment. Current response calls update individual assignments. Concurrent client calls do not make a grouped answer atomic.

## Steps

1. Define a pure schedule view model grouped by active organization, Person and plan ID, using stable assignment IDs. Preserve each team/position/status and deduplicate attendance times by ID while retaining which position requires them. Sort by actual service date/time. Lift reusable logic into shared only if multiple clients need it. **Done:** a fixture containing two positions and different statuses renders one complete plan group without losing either assignment.
2. Add All/Pending/Confirmed/Declined filtering and explicit upcoming/history behavior using supported API parameters. Define group matching as “at least one assignment matches”; show every position on a matching card so filtering cannot hide another responsibility. Represent mixed status as mixed, never as a single misleading confirmation. **Done:** tests cover mixed groups, duplicate times, empty results and date ordering.
3. Replace the plan screen's first-match personal-assignment display with all of the person's applicable assignments and attendance times. Use clear individual response controls until a verified grouped atomic endpoint exists. **Done:** both schedule and plan detail show the same responsibilities and answer scope.
4. Add decline-reason input, optional unless the current policy requires it, with shared length validation. Preserve the draft on failure. Add deliberate “Withdraw confirmation” review for a confirmed assignment; submit a decline with its reason and record the prior response/history at the server. Declined requests cannot be silently resurrected by retry or re-accept; require an explicit scheduler re-request/reassignment path and enforce this server-side. **Done:** all state transitions are explicit, permitted and auditable; a client cannot bypass policy by calling the route directly.
5. Track pending/error/success by assignment ID. Retry the exact original scope; disable duplicate submits. On success, refresh affected schedule, plan, calendar and notification queries in the active context. If independent responses partly succeed, report each result and keep failed drafts. **Done:** a timeout or partial failure cannot produce a false “all confirmed” banner.
6. If MOB-005's atomic snapshot endpoint is available, add grouped review showing exact positions/times and expected version, then call it once. Otherwise keep individual controls and record grouped answer support as dependent on MOB-005. Never implement “Respond to all” as a loop presented as atomic. **Done:** the UI's scope matches the server transaction boundary.
7. Add meaningful behavior tests for grouping/filtering, all assignments on a plan, confirmation withdrawal, reason persistence after failure, forbidden transitions, stale state and partial independent failures. Run common checks and inspect the native forms with keyboard/large text. **Done:** the progress note distinguishes implemented individual behavior from any pending grouped gate.

## Acceptance checks

- A plan with two roles, two teams or different attendance times loses no responsibilities in either view.
- Mixed statuses and filters are truthful; no position disappears just because another one matched.
- Confirmed withdrawal requires deliberate review, retains the original response history and informs the appropriate authorized scheduler after commit.
- Failed submissions retain reason and exact assignment scope; unrelated organizations are untouched.
- Grouped responses, if exposed, are atomic and versioned through MOB-005.

**Handoff:** list response transitions supported and whether grouped actions are available. Continue with MOB-005's first incomplete pass.
