# MOB-010 — Decline, request and track a replacement

Read [the common instructions](README.md) first. Requires MOB-004 withdrawal/reason behavior, MOB-005 identity/request/attendance/outbox contracts, MOB-008 candidate scope and MOB-009 transactional allocation. Work backend first, then native.

**User story:** As a volunteer who cannot serve, I keep an honest declined answer and request help finding a replacement. As a leader, I review eligible offers; a replacement receives their own request and explicitly consents before becoming confirmed.

**Read:** mobile specification replacement policy; Services F07; US-07.2; MOB-009's implemented contracts and tests; existing assignment response, candidate/conflict, notifications and native schedule/plan code. US-07.3 swaps are a later extension, outside this task.

**Policy for this implementation:** use leader-approved offers and a new recipient response. The reference product's coordinated auto-confirm behavior is not the Service Center default. Any future alternate policy needs explicit team configuration and acknowledged coordination; do not silently infer it from the original volunteer's request.

## Pass A — State, permissions and shared capacity

1. Define replacement-request and offer DTOs/state transitions in shared contracts. A request references the original assignment, Person, plan/position/time scope and expected version. Keep the original declined record and response history. A confirmed person must deliberately withdraw through MOB-004 before opening a replacement request. Permit one unresolved request per original vacancy; retries return that request. **Done:** creating a request cannot delete the original assignment or copy its answer to another Person.
2. Use an explicit lifecycle such as request open → offered → filled/cancelled/expired, and offers pending → accepted-awaiting-approval → finalized or rejected/expired/superseded. Pending invitations alone do not reserve every offered seat. Candidate acceptance reserves available capacity through MOB-009; leader approval finalizes after revalidation. If approval occurs before consent, it authorizes an offer but does not confirm the candidate. Persist author/time/revision and a finite offer/reservation expiry. **Done:** every state has defined actor, capacity effect and next valid transitions.
3. Read the database skill, add additive persistence/RLS and implement request creation/cancellation, authorized candidate search, offer issue/decline/accept and leader approve/reject/finalize. Use current route naming conventions; proposed `/replacement-requests` and nested `/offers` are contracts to add. Check current organization, ownership, team leadership and recipient on every read/write; generic volunteer views must not expose a private contact directory. **Done:** a requester cannot accept an offer for another candidate, and an unrelated leader cannot read/update the request.
4. Recheck candidate eligibility, actual attendance conflicts/preferences and version at each critical transition. Use the exact allocator/lock order from MOB-009 for accepted reservations and finalization. A candidate who explicitly accepts the current scope may receive a new confirmed assignment after required leader approval; a leader issuing a request without that consent leaves it unconfirmed. Scope changes invalidate prior consent. **Done:** no confirmation derives solely from the original volunteer's answer or a stale offer.
5. Finalize transactionally: preserve original history, validate/reserve/fill capacity once, create/link the replacement assignment, mark the request filled and close competing offers. Reuse a winning candidate's matching existing assignment only when its identity/time scope is equivalent and the operation is explicitly idempotent. Superseded offers cannot later confirm or release someone else's reservation. **Done:** two candidates, a signup and manual scheduling cannot all fill the same vacancy.
6. Queue requester/candidate/scoped-leader updates through the existing outbox after commit; deduplicate by persisted transition ID. Exclude private decline reasons from broad feeds or lock-screen bodies. Expire/release reservations using MOB-009's bounded lifecycle; membership removal or material plan changes invalidate actionability safely. **Done:** retry, rollback and expiry produce neither duplicate updates nor immortal capacity reservations.
7. Write real transactional tests for duplicate request/offer acceptance, two-candidate final-slot race, replacement versus signup/manual fill, accept/approve order, stale times, unauthorized recipient/leader, expiry, cancellation and rollback. Assert the original decline/history remains intact after every failed or successful outcome. **Done:** final assignment count and state history prove exact once-only filling without losing original answers.

## Pass B — Native request and tracking flow

8. From a declined/withdrawn assignment, add “Request a replacement” with review of position, times, reason audience and what approval means. Keep the decline action separate and truthful if replacement creation fails. Show request status and permitted cancellation in the plan/schedule group; retain original response information. **Done:** the user can distinguish “I declined” from “a replacement is confirmed.”
9. Add a scoped leader view for eligible candidate preview and offer/approval tracking within the plan Teams area. Show redacted conflicts, exact times and current capacity. If requesters may suggest a candidate, suggestions need existing authorized visibility and do not assign anyone. **Done:** candidate selection uses shared eligibility and cannot silently override hard conflicts or expose private roster fields.
10. Show candidate offer details with explicit accept/decline, current required times and pending-approval/final status. Use snapshot versions/idempotency, disable duplicate submits and refresh before retry after an unknown result. Mark full/stale/expired/superseded outcomes clearly; offline clicks are not saved commitments. **Done:** candidate consent and leader approval can be followed end to end in native and persisted state.
11. Refresh scoped schedule, plan, openings, request/offer and notification queries after successful transitions. Run common checks and inspect multi-role cards, long names, error states and both themes. **Done:** an expired offer or organization switch cannot leave an actionable stale confirmation control.

## Acceptance checks

- The original declined assignment and audit history survive; the replacement has their own identity and answer.
- Default confirmation requires the candidate's fresh consent and the leader's approval in either supported order; scope changes require fresh review.
- Every competing acceptance/claim/manual-fill path shares MOB-009's database capacity enforcement.
- Requester, candidate and leader see only their authorized information and actions; invalid, expired, used or superseded offers are safe.
- Retries are idempotent, expired reservations release once, notifications follow committed state, and failure never appears as a completed replacement.

**Handoff:** record state machine, approval/consent behavior, history preservation, concurrency test evidence and any pending native/device gates. This finishes the selected prompt range; MOB-011 and later remain separate backlog work.
