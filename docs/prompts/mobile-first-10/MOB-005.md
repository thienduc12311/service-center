# MOB-005 — Prepared/released requests and exact attendance responses

Read [the common instructions](README.md) first. **Execute one lettered pass per invocation.** This task is substantially larger than a native screen. Passes A–D establish shared contracts; Pass E connects native. Recheck which passes are already implemented before starting.

**User story:** As a leader, I prepare requests privately and release the reviewed scope. As a volunteer, I answer only the positions and attendance times shown to me, including a reviewed batch, without accidentally answering later changes.

**Read first:** mobile specification MOB-004/MOB-005 and §7; Services specification F01/F02/F04/F08; US-02.1/02.2, US-04.1/04.2 and US-08.1/08.3; ADR 0001–0003. Then load the source paths for the selected pass below.

**Required distinctions:** Person is roster identity; Profile authenticates. Prepared/released is audience visibility, not answer status. Publication is not request release; suppressed email is not private preparation. Confirmation is not actual attendance. A displayed request version identifies exact assignments and applicable plan-time IDs.

## Pass A — Scheduling identity and scoped access

**Inspect:** shared database/domain/people/team/assignment types and schemas; `backend/src/model/people.ts`; people/team/assignment routes; auth/organization middleware; existing `supabase/migrations/` and RLS; website `SchedulePeopleModal.tsx` and `TeamsTab.tsx`.

1. Inventory the existing `people` table, profile links, mixed roster IDs, team memberships, assignments, notifications and token records. Person rows already exist; assignments and some memberships still use Profile/user IDs. Identify ambiguous legacy links and every user-ID assumption before proposing a migration. **Done:** a mapping table names old identity, new canonical Person reference and compatible behavior for each affected contract.
2. Read the database skill and implement additive Person references using existing linked rows, backfilling missing organization-member Persons idempotently. Retain assignment IDs, statuses, authors, timestamps, feed identity and outstanding response links. Never create placeholder auth users or merge by email alone. Keep old readers/writers working during transition; a no-login assignment must be readable without a mandatory Profile join. **Done:** fixtures for linked members, unlinked existing members, no-login Persons and ambiguous links produce deterministic migration results with no history loss.
3. Add the minimum persisted team/service-type leadership scope required by these ten tasks, preserving existing organization owner/admin/scheduler access. Define shared capability checks for prepare/release/schedule/respond/view. Enforce the same scope in RLS and backend privileged operations. Members can answer their own released requests, not alter assignment ownership, team, times or release state through direct table updates. **Done:** both direct SQL under caller role and API tests deny cross-organization/unauthorized-team writes while preserving valid leader actions.
4. Update shared types/client and web compatibility adapters before enabling no-login scheduling. Account invitation acceptance links the existing Person without moving or recreating assignment history. **Done:** existing web staffing still works; a no-login Person can hold an assignment and later acquire a login with the same history. Record any ambiguous real-data reconciliation as an explicit rollout gate.

## Pass B — Stable times and assigned attendance scope

**Inspect:** plan schema/routes/services, `plan_times`, current `scheduling_conflicts` RPC, assignment routes, calendar/feed generators and shared date helpers.

1. Replace unsafe list-position time mutation with stable time IDs and expected plan/time revisions while keeping compatible old payloads safe. Add assignment applicability for all required times versus an explicit selected subset; persist per-time answers if the native split response can differ by time. Validate every time belongs to that assignment's plan and organization. **Done:** reorder changes order, not identity; deleting/changing a referenced time has an explicit impact/stale-version response.
2. Compute actual required intervals, including rehearsal/other attendance, using half-open overlap semantics. Define the fallback for genuinely untimed legacy plans and the policy for newly added times in “all” mode. Repeating an identical commitment on the same plan is not double booking, but different incompatible same-plan obligations must not be globally ignored. **Done:** tests cover rehearsal-only overlap, touching boundaries, separated services and same-plan collisions.
3. Update shared schedule/plan/API shapes so native and web can display exact assigned times and mixed answers. Invalidate request versions when time edits alter promised attendance; keep calendar event IDs stable and update sequences per existing ADRs. **Done:** time changes cannot leave an old preview apparently current, and old clients still read coherent assignment summaries.

## Pass C — Versioned request snapshots and atomic answers

**Inspect:** `backend/src/routes/assignment-respond.ts`, `assignments.ts`; token and notification services; shared response schemas/client; current SQL token/RLS tests.

1. Model a request snapshot identifying recipient Person, organization/plan, exact assignment IDs, attendance scope and expected revisions. A grouped batch carries explicit snapshot IDs and versions; never infer its scope again from “all current assignments.” Use typed preview/commit contracts, selecting names consistent with existing APIs. **Done:** a fixture proves a later-added assignment is outside an earlier request.
2. Implement one database transaction for permission/version checks, response/history updates, token consumption and durable side-effect intents. Define deterministic invalid/expired/used/stale outcomes. An authenticated batch across selected requests is all-or-nothing for the scope shown in its review. Reuse an idempotency identifier for authenticated transport retries; public single-use token replay remains explicitly rejected. **Done:** forced failure rolls back every answer and token consumption; concurrent token submits have one winner.
3. Keep public links minimal and rate limited, with hashed token storage and no full-plan privilege. Migrate outstanding legacy links to an explicit, recorded scope before enabling snapshot behavior; invalid/ambiguous links require safe reissue rather than silently expanding scope. Preserve the ADR's Person/plan grouping while refining it to exact recorded assignments. **Done:** legacy-token tests show preserved or safely rejected scope and no changed unrelated positions.
4. Consolidate authenticated/public response effects through the same service. Retain original answers/history and support deliberate confirmed withdrawal without silent declined→confirmed resurrection. Record scheduler notification intent once after a successful response transaction. **Done:** both response entry points produce identical history and scheduler outcomes for the same permitted transition.

## Pass D — Private preparation, explicit release and durable effects

**Inspect:** all assignment reads/writes, plan detail joins/counts, schedule/calendar/feed routes, notification/email/push services, direct Supabase access/RLS and website staffing controls. Search the repository for assignment table usage, not just native screens.

1. Add separate persisted preparation/release state with a compatible legacy migration. Existing visible requests remain released unless there is explicit evidence otherwise; do not interpret every old `notify:false` as prepared. Expose a scoped leader preview and release command with expected versions. **Done:** a leader can read prepared rows while their recipient cannot obtain them through RLS, API, joined counts or privileged exports.
2. Audit every output channel: member plan/schedule lists, counts, calendars, ICS/subscription feeds, public responses, in-app notifications, email and push. Apply visibility at the data boundary, including `adminDb` paths. **Done:** prepared fixtures are absent from every recipient surface, not merely hidden by UI.
3. Release the reviewed set atomically and enqueue durable effects in that same transaction. Group per Person/plan; generate snapshot links and send only after commit. Use existing transport adapters and implement a bounded outbox/retry dispatcher if none exists. Keep external provider calls outside database locks. Expose queued/provider-accepted/simulated/failed outcomes honestly; retry must not create another request or duplicate event. Publishing a plan alone sends nothing. **Done:** rollback sends nothing, transport failure preserves retryable intent, and duplicate release is idempotent.
4. Preserve existing website scheduling through compatible adapters or small explicit prepare/release controls. Full reminder-policy editors and new infrastructure providers remain outside this task. **Done:** website reload reflects the same state and cannot bypass private preparation or atomic response rules.

## Pass E — Native review, split and batch responses

**Inspect:** `mobile/app/(tabs)/index.tsx`, `mobile/app/plan/[id].tsx`, native response route from MOB-003, shared primitives and query keys.

1. Extend MOB-004's plan groups with exact applicable times, per-scope states and clear mixed summaries. Offer pending-response selection and a review listing every selected position/time before commit. Use only the snapshot/atomic API. **Done:** the review payload and committed scope are identical and query refresh cannot silently add rows to a pending submit.
2. Handle stale requests by showing what changed and requiring a fresh review; preserve reason drafts where still applicable. Show prepared/released controls only to authorized leaders; volunteers never see prepared content. Disable duplicate submissions, show truthful offline/error states, and refresh scoped schedule/plan/calendar/notification queries after success. **Done:** server errors leave the screen consistent with persisted state.
3. Verify the complete flow with fixtures: prepare → absent for recipient → preview/release → snapshot response → scheduler update. Include a no-login public response, split times, mixed position answers and a stale bulk review. **Done:** all acceptance checks below have evidence, with native device gates separately recorded.

## Full-task acceptance

- Linked/no-login identities work without duplicate Persons, stub auth accounts or lost historical records.
- Prepared requests cannot be discovered by their recipient through any supported data/delivery path; release is authorized, explicit and idempotent.
- Every answer changes exactly the previewed assignments/times. New assignments, changed times, expired/replayed links and stale versions cannot expand that scope.
- SQL integration tests exercise RLS and real concurrent transactions, including duplicate response, release rollback and stale batch; mocked service tests alone are insufficient evidence for atomicity.
- Website behavior remains compatible, shared/backend tests and builds pass, and native iOS/Android export plus available interaction checks pass.

**Handoff:** report the selected letter, contracts/migrations/services added, compatibility and rollout gates, exact tests and the next letter. Mark MOB-005 complete only after A–E and their gates; broader F01/F02/F04/F08 epics may still have out-of-scope work.
