# F07 — Volunteer signups, replacements and approved swaps

Read [execution rules](../IMPLEMENTATION-RULES.md). **User story:** Eligible volunteers claim an opening or help fill a decline, while leaders can trust capacity and the original answer history.

**Read:** Services spec F07; US-07.1/07.2/07.3; F01/F02/F04/F08; [MOB-009](../mobile-first-10/MOB-009.md) and [MOB-010](../mobile-first-10/MOB-010.md) detailed shared contracts; backend assignment/plan/team routes, shared needs/types/client and web TeamsTab. Reuse any allocator already delivered by those mobile tasks.

## Pass A — One capacity transaction

1. Define opportunity policy, deadline, eligibility, applicable times and capacity versus plan needs. Model direct-confirmation claims and leader-approval reservations with finite expiry, idempotency and audit. Use proposed `/plans/:id/opportunities` naming only if compatible with the already implemented client; select one API family. **Done:** all states have explicit capacity effects and current server-time validation.
2. Build/reuse one transactional allocation boundary with stable locks covering overlapping plan/position/time scopes. Include occupying assignments and active reservations; exclude declined/expired/superseded rows. Integrate manual assignment/status/time/needs changes so another writer cannot bypass capacity. **Done:** real two-connection tests yield one winner for the last slot across signup/manual/approval paths.

## Pass B — Signup web/shared flow

3. Add authorized opportunity setup/edit/close, eligible list/detail/preview, idempotent claim/cancel and leader approval/rejection. Recheck membership/conflicts/version/deadline at commit and hide private roster/prepared counts. **Done:** a real leader/member fixture can complete signup without direct DB edits.
4. Add web opening/approval UI with explicit direct-confirmed versus awaiting-approval state, bounded expiry and truthful outcomes. Queue committed effects through F00/F08. Native MOB-009 consumes the same contracts. **Done:** cancel/reject/expire releases once, and retries cannot create duplicate commitments.

## Pass C — Replacement and history

5. Add one unresolved replacement request per original declined/withdrawn vacancy; keep original assignment/answer/history intact. Issue eligible offers with recipient-specific consent/version and leader approval by default. Candidate acceptance reserves capacity using Pass A; finalized assignment is new or explicitly reconciled idempotently, never copied consent. **Done:** original answer survives and competing offers/signups/manual fills cannot overfill.
6. Add leader tracking across bounded plans plus requester/candidate state views, explicit expiry/cancel/supersession and auditable notifications. A coordinator's offer without recipient consent remains an unconfirmed request. **Done:** users can distinguish a request for help from a confirmed replacement; MOB-010 uses the same state machine.

## Pass D — Optional approved swaps

7. Model two linked replacement operations with both Persons' explicit consent, valid attendance/conflicts and required leader approvals. Lock/revalidate both sides and finalize together; cancellation/expiry releases both reservations safely. **Done:** failed/stale second side leaves neither participant secretly reassigned or over capacity.
8. Run API/RLS/history tests and real races for claim/claim, offer/offer, signup/replacement/manual and swap rollback. **Done:** stored capacity, audit and outbox records reconcile after every outcome.

**Acceptance:** exact eligible scope, one allocator, honest approval state, preserved original history and no copied/implicit consent. Wider public signup needs separate publication policy.

**Handoff:** API/state machine, occupancy rules, competing writers integrated, concurrency evidence and optional swap status.
