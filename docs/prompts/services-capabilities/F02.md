# F02 — Person-first staffing and reversible roster lifecycle

**Current status:** Read [the cross-feature audit](../../plans/services-mobile-contract-audit.md) and the latest [progress entry](../../plans/services-capabilities-progress.md) before choosing a pass. The steps below define scope; implemented passes are verification work, not a request to rebuild them.

Read [execution rules](../IMPLEMENTATION-RULES.md). **User story:** A scheduler assigns a guest before login, and that same Person retains their service history when they later join the organization.

**Read:** Services spec F02; US-02.1/02.2/02.3; existing people table/migrations and `backend/src/model/people.ts`; people/team/assignment/invitation routes; shared Person/roster/database/schemas; web People/Person pages and SchedulePeopleModal. Inspect MOB-005 Pass A and existing token contracts first.

## Pass A — Additive identity migration

1. Inventory every profile/user-ID assumption in assignments, memberships, blockouts, requests, notifications, conflicts and roster UI. Existing Person rows already support no-login people; do not create another roster model. **Done:** mapping identifies reusable linked rows, legacy members needing a backfill and ambiguous cases requiring reconciliation.
2. Add canonical same-organization Person references with idempotent backfill and compatible dual-read/write. Preserve row IDs, answers, authors/timestamps, feed identity and outstanding response links. Keep nullable/no-profile joins valid and enforce explicit profile-person link uniqueness; never merge by email or create fake auth accounts. **Done:** linked, unlinked-member and no-login fixtures migrate without duplicate identity or lost history.
3. Update shared inputs/client/services to accept `person_id` while safely supporting legacy callers. Reuse F01 authorization and F08 response snapshot semantics where available. Defer destructive removal of legacy columns to a separately validated migration. **Done:** web/native and token readers can resolve both transition formats consistently.

## Pass B — Guest staffing and account continuity

4. Add existing-Person selection and minimal guest creation to the web scheduler, with missing-email warning and optional separate organization invitation. A plan-only guest need not become a permanent team member. Add plan-only temporary positions with label/team owner and valid needs/assignment links, without changing global team positions. **Done:** a no-login guest receives a scoped response link and can answer without account onboarding.
5. Link invitation acceptance to the existing Person and retain all assignments/links. Test concurrent linking, foreign organization, duplicate/ambiguous email, inactive Person and no email. **Done:** acquiring a login changes access resolution, not service history or identity.

## Pass C — Roster extensions

6. Add reversible archive/restore with audit and picker exclusion, preserving historical staffing and disabling new actionability appropriately. Add skills/tags/groups and previewed bulk team/tag changes with atomic scope. Global search returns permission-filtered entity projections, including restricted snippet/count handling. **Done:** archive is distinct from deletion and restricted entities/fields cannot be found through search.
7. Run migration, API and caller-role SQL tests plus shared/backend/web checks; check dependent native types/exports when contracts change. **Done:** all compatibility and history cases have actual evidence.

**Acceptance:** no-login staffing, stable account linkage, old-token continuity and no duplicate Person creation. Full roster extensions are separately tracked from core identity.

**Handoff:** migration phases, unresolved data ambiguities, compatible API shapes and completed native prerequisites.
