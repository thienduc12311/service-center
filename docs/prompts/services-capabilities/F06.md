# F06 — Rotations and explainable staffing proposals

**Current status:** Read [the cross-feature audit](../../plans/services-mobile-contract-audit.md) and the latest [progress entry](../../plans/services-capabilities-progress.md) before choosing a pass. The steps below define scope; implemented passes are verification work, not a request to rebuild them.

Read [execution rules](../IMPLEMENTATION-RULES.md). **User story:** A leader proposes several weeks of staffing, understands each choice and unmet need, adjusts the result and commits prepared requests without overwriting manual commitments.

**Read:** Services spec F06; US-06.1/06.2; F03 preferences, F04 conflicts, F05 workspace and F08 preparation services; F10 roster/template rules when relevant; shared Person/team/needs contracts and existing assignment writers.

## Pass A — Deterministic proposal engine

1. Define bounded immutable input snapshots: plans, needs, eligible position memberships, attendance, blockouts, preferences, current/locked assignments, serving lookback and rule version. Authorize every input. **Done:** a snapshot can be replayed without reading changing live state or leaking hidden people/assignments.
2. Implement a pure deterministic engine. Hard constraints exclude ineligible/unavailable/conflicting choices; preserve confirmed and locked/manual assignments. Minimum fairness orders lower assigned count in configured lookback, then least recently served, then stable tie-break/recorded seed. Leave impossible needs open with binding reasons. **Done:** same snapshot/rules/seed produces the same choices and explanations; no model service is required.
3. Persist proposal identity, input revisions, rule version, author and expiry. Expose unmet needs/warnings and reasons for each candidate choice. **Done:** preview creates no assignments, release or notification effects.

## Pass B — Rotation rules and review

4. Add versioned team rotation CRUD for repeating eligible Person/position patterns, cycle length and exceptions. A rotation suggests choices but cannot bypass current membership/conflicts. Define local-week/DST date semantics and explicit handling for missing people. **Done:** a changed or expired pattern produces a warning/vacancy rather than an invalid assignment.
5. Integrate proposal review into F05 with adjust/lock/unlock controls and a visible actual fairness policy. Recompute dependent choices after edits; household together/apart rules only apply after explicit F03 grants/preferences exist. **Done:** manual locks survive recomputation and unsupported household assumptions are absent.

## Pass C — Prepared commit

6. Commit the reviewed proposal atomically/idempotently through canonical assignment services, rechecking capabilities, all input revisions, conflicts and capacity. Stale inputs require refresh/recompute. Commit as prepared; release is a distinct F08 action. **Done:** a collision or changed membership cannot create partial/visible requests or overwrite manual choices.
7. Test fairness ties, insufficient skills, contradictory preferences, repeat-cycle exceptions, locked confirmed work, two simultaneous commits, stale blockout and rollback. Use meaningful deterministic fixtures and real transaction tests for commit. **Done:** explanations match selected constraints and produced rows match reviewed scope.

**Acceptance:** explainable deterministic suggestions, preserved commitments, honest vacancies, no preview side effects and race-safe prepared commit. Fairness metrics describe policy, not a guarantee of perfect equitable outcomes.

**Handoff:** rule/count definitions, proposal inputs/version, rotation semantics, tests and any unresolved policy options.
