# MOB-016 — Edit simple notes, then scoped note categories

Read [execution rules](../IMPLEMENTATION-RULES.md). **User story:** As a planner, I save useful plan notes from my phone; as a volunteer, I see only the note audience I am allowed to read.

**Read:** mobile spec planning/notes section; US-09.1; [F09 prompt](../services-capabilities/F09.md); native plan detail; website `EditNotesModal.tsx`, `PlanSidebar.tsx`; shared plan schema; backend plan read/update and exports.

## Pass A — Existing plan notes

1. Trace existing plain notes read/write behavior and current audience. Add a minimal expected-revision contract if missing; preserve existing web compatibility. **Done:** capability, validation length and conflict behavior are explicit without inventing private categories in a public notes string.
2. Add a native edit sheet using shared primitives, multiline input, keyboard-safe scrolling, save/cancel and unsaved-change review. Preserve draft on failed save, and require a deliberate refresh/merge after stale edit. **Done:** success reloads the actual saved note on both clients; failure keeps the user's text.
3. Gate editing by server capability, render text safely and refresh scoped detail queries. Test empty-note clearing, long text, denied update, concurrent edit, timeout and organization change. **Done:** no cross-plan draft leakage or lost edit; applicable checks pass.

## Pass B — Categories and team audience

4. Implement/reuse F09 categorized-note persistence and access, including author, category, parent, team audience and revision. Add native category/audience selection with an explicit preview of visibility. A title or locally hidden section is not an access boundary. **Done:** every private category is protected by API/RLS and absent from unauthorized joins, search and counts.
5. Display only authorized categories in the workspace, respecting item/plan distinction. Connect item responsibility/selected columns only through implemented F11 contracts. Keep private text out of public response pages, notifications, print/export and rehearsal manifests. **Done:** direct reads and generated outputs obey the same audience as the screen.
6. Test team membership change, prepared-request-only access, foreign category/parent IDs, revision conflict and private-note export/push leakage. Run permission/SQL tests plus native export and accessible form checks. **Done:** revocation blocks future reads and changing audience is an audited authorized action.

**Acceptance:** simple notes can ship independently; full categories require actual shared access enforcement. Neither a successful API call nor hidden native content alone proves private notes are secure.

**Handoff:** completed pass, current audience semantics, tested output channels and any category/responsibility dependencies still pending.
