# MOB-030 — Existing media browsing and optional iOS PDF scanning

Read [execution rules](../IMPLEMENTATION-RULES.md). **User story:** As a planner, I open an existing media bundle and attach permitted files; on a supported iOS device, I can deliberately scan pages into a PDF attachment.

**Read:** mobile spec media/scan section; [F14 prompt](../services-capabilities/F14.md) media stage; F13 file contracts; MOB-026 native upload/preview. Current songbook documents are not media bundles, and OCR was deliberately removed.

## Pass A — Read existing media

1. Verify/implement F14 media metadata and permitted file listing. Add a bounded native read-only browser/detail with title, duration, creator/thumbnail/tags and actual supported file types. **Done:** only authorized existing records/files appear and archived/removed records have safe states.
2. Permit attaching/selecting existing media only through implemented F11/F13 parent/link contracts. Keep media separate from songs/arrangements and retain file rights/version policy. **Done:** an order item resolves the actual media bundle without fabricating a song identity or widening file access.
3. Reuse MOB-026 previews/share/upload lifecycle for permitted file operations. Full media-record create/edit stays on web initially. **Done:** media browsing works independently of a native authoring feature and unsupported actions are absent.

## Pass B — Optional iOS scan

4. Research current official iOS scanner APIs/module compatibility, camera permission and development-build requirements. Choose a supported multipage PDF path and verify local processing/storage behavior. Android scanning is a separate selection. **Done:** feasibility lists tested devices/builds and an unavailable-feature fallback without claiming Expo Go proves support.
5. Add an explicit Scan action with permission recovery, page review/reorder/delete and cancel. Upload the resulting PDF through F13 intent/finalize, with size limits and temporary-file cleanup. No extracted text, song parsing, AI/OCR provider or quota system is implied. **Done:** canceled scans create no ready attachment, and reviewed PDF bytes use the same audience rules as an ordinary upload.
6. Test denied camera, unavailable scanner, canceled capture, multi-page PDF rendering, upload interruption and revoked parent access. Run common checks and physical iOS scanner tests. **Done:** record byte-level PDF/Storage evidence and unsupported-platform state separately.

**Acceptance:** actual authorized media browsing/linking; optional scanning produces a user-reviewed PDF through the existing file lifecycle. OCR restoration and native media-record authoring remain outside the selected stage.

**Handoff:** stages delivered, SDK documentation/build requirements, file/privacy checks and remaining device gates.
