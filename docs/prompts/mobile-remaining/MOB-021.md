# MOB-021 — Appearance, account settings and help

Read [execution rules](../IMPLEMENTATION-RULES.md). **User story:** As a phone user, I keep my chosen appearance after restart and find help, version and permission controls in predictable settings.

**Read:** mobile spec settings section; MOB-001 token/Pressable fixes; `mobile/src/lib/theme.ts`, `useTheme.ts`, native profile tab/root layout, AuthProvider, `mobile/app.config.js`; website ThemeProvider/settings as vocabulary references. Reuse installed storage and OS color-scheme APIs.

## Steps

1. Trace current light/dark state and hydration. Define typed light/dark/system preference, storage scope, initial loading policy and reset-to-system behavior. Effective system mode follows OS changes without overwriting an explicit choice. **Done:** the app cannot flash an arbitrary saved scheme after protected content is visible.
2. Implement persistence and a system option using existing theme adapters, maintaining shared colors and native navigation/splash behavior as far as supported. Keep chart fonts separate from UI. **Done:** restart, OS theme change and manual reset produce predictable effective colors without reintroducing editorial styling.
3. Organize settings into account, active organization, appearance, notifications, help/about and storage when caching exists. Display actual app/build version from supported configuration; provide real configured help/contact links and permission recovery links. Avoid dead links or invented support addresses. **Done:** all visible settings perform a working action or show a clear unavailable state.
4. Separate organization management from account sign-out/delete semantics. Reuse MOB-003 sign-out cleanup. When MOB-025 exists, offer bounded account-owned cache removal with size/confirmation; until then, omit a fake cache manager. **Done:** changing theme never changes account/org, and clearing files cannot delete another account's data.
5. Add meaningful state/persistence tests where a harness is appropriate; manually verify startup, theme change, error/retry storage access, large text, screen reader, keyboard forms and both schemes. Run typecheck/native exports. **Done:** tests prove preference transitions rather than duplicating token constants, and device-only gaps are explicit.

**Acceptance:** light/dark/system persists, system mode follows the OS, settings use consistent website terminology, help/version are factual and account/cache actions stay correctly scoped.

**Handoff:** persistence policy, verified settings destinations and device matrix. Full organization administration or account deletion is outside this task unless separately implemented.
