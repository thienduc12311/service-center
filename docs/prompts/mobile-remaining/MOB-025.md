# MOB-025 — Explicit offline rehearsal downloads and cache management

Read [execution rules](../IMPLEMENTATION-RULES.md). **User story:** As a musician, I deliberately prepare permitted materials offline and know which versions are ready, expired or failed.

**Read:** mobile spec offline section; US-14.3; [F14 prompt](../services-capabilities/F14.md) offline stage; MOB-024 playback ownership, F13 file/version rights and MOB-003 cleanup. Inspect installed filesystem/storage support before adding an Expo-compatible package.

## Steps

1. Define a cache entry/manifest keyed by authenticated account, organization, plan/item and immutable file version. Store size/integrity, rights, downloaded time and policy expiry. Use the proposed 30-days-after-plan audio expiry only as an explicit documented Service Center policy, configurable through the shared contract. **Done:** no private pack can be resolved under another account or organization.
2. Extend/reuse F14 manifests for download permission and expiry; stream permission alone is insufficient. Create a bounded download queue and explicit per-track/plan user action. Download into temporary files, verify size/hash and atomically finalize; either support verified resume or clearly restart interrupted downloads. **Done:** partial bytes are never labeled ready.
3. Integrate ready/downloading/failed/stale/expired states into rehearsal. Prefer the exact authorized cached version; show unavailable offline instead of silently opening an unrelated/newer file. Recheck rights/versions on reconnect and stop serving expired/revoked entries locally when known. **Done:** player and chart context identify the actual prepared version.
4. Add storage totals, cancel/retry and selected/all account-owned removal in settings. Clear account private files on sign-out according to the documented policy and prevent stale jobs from recreating them after cleanup. Use supported secure storage/OS file-protection choices for sensitive metadata. **Done:** late downloads cannot attach an old user's file to a new session.
5. Keep schedule/response writes online; offline reading does not imply an offline mutation queue. Describe offline revocation limits honestly: already downloaded bytes cannot be erased remotely while disconnected. **Done:** UI states its expiry/access policy without promising immediate remote wipe.
6. Test interrupted/network-loss download, low storage, hash mismatch, concurrent cancel, expired manifest, file version replacement, sign-out during download, restart recovery and user/org switch. Run common checks plus real device filesystem/background tests where supported. **Done:** cache accounting matches actual finalized files and failures are recoverable.

**Acceptance:** opt-in authorized exact-version downloads, no partial-ready state, bounded/visible storage, expiry and account isolation, and coherent offline playback without false committed writes.

**Handoff:** policy/rights contract, download state machine, cleanup evidence and remaining platform checks.
