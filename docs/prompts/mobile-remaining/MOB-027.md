# MOB-027 — Advanced playback, car integrations and Siri

Read [execution rules](../IMPLEMENTATION-RULES.md). **User story:** As a musician, I use a supported advanced rehearsal tool without losing basic playback reliability or exceeding media rights.

**Read:** mobile spec advanced playback section; US-14.3; [F14 prompt](../services-capabilities/F14.md); implemented MOB-024 adapter/state machine, file rights and app build configuration. This is optional work after stable playback, with independent feature stages.

## Pass A — Feasibility and selection

1. Inventory current runtime, native build workflow, media sources and rights. Research current official platform/module documentation for loops, metronome, local speed/pitch processing, CarPlay, Android Auto and Siri separately. Record supported platforms, entitlement/review requirements, native modules, licensing and device test needs. **Done:** a feasibility table has primary-source links and a reproducible small spike for each proposed supported path; Expo Go is not entitlement evidence.
2. Select one named stage for this invocation: B loops/metronome, C audio processing, or D one car/voice platform. If selection is missing, finish feasibility and present bounded choices; leave entitlement-dependent stages pending. **Done:** scope and success/device gates are explicit rather than a broad “car integration” promise.

## Selected implementation stage

3. **B:** extend the single player with repeatable A/B loop boundaries and a separate, explicitly configured tempo/metronome source. Validate seek/track transitions and stop/clear loops at context change. **Done:** boundary/tempo behavior is tested without duplicate audio sessions.
4. **C:** process only authorized local media through the verified adapter. Keep source/version immutable, label actual speed/key processing and distinguish it from chart-only transposition. Bound CPU/storage and provide fallback on unsupported codecs/devices. **Done:** audible output and displayed key/speed agree, with measured supported-device behavior.
5. **D:** connect one supported platform to the existing media session, minimal permitted browse/play intents and validated account/organization context. Handle denied/unavailable entitlement and signed-out state safely. Never expose planning edits through driving UI. **Done:** actual approved development build responds to device controls and cannot resurrect old-account playback.
6. Test the selected stage for interruption, disconnect, revoked file rights, background/foreground and resource use. Run common checks and physical-device tests. Record unselected/unsupported stages separately. **Done:** the selected capability has evidence; other capabilities remain gated.

**Acceptance:** stable basic playback, explicit rights/build support, coherent state and real-device verification for the selected stage.

**Handoff:** selected stage, source links, feasibility results, implementation/tests and entitlement/device gates; never mark all advanced platforms complete from one spike.
