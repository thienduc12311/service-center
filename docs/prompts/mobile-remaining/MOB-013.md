# MOB-013 — Create plans and apply templates

Read [execution rules](../IMPLEMENTATION-RULES.md). **User story:** As an authorized planner, I create a dated plan from my phone and, once supported, review several dates or a saved template before committing them.

**Read:** mobile spec planning section; US-10.1/10.2; [F10 prompt](../services-capabilities/F10.md); native Plans/plan workspace; `frontend/src/pages/PlansPage.tsx`, `ServiceTypeWizardPage.tsx`, plan template/import components; backend plan routes/services; shared plan/service-type schemas and API client.

## Pass A — One dated plan

1. Verify the current create API, service-type access, timestamp/date intent and duplicate-submit behavior. Add an idempotent create contract and organization-timezone validation if missing. A service type is not a saved template. **Done:** submitting one valid draft twice with the same key returns one plan with stable IDs.
2. Add a create form for permitted service type, title, local date, location and supported initial times. Show timezone, validate required fields and preserve draft on failure. Offer existing supported defaults without pretending that a saved template system exists. **Done:** created plans reload correctly on web/native, and DST/invalid dates have explicit errors.
3. Test denied creation, foreign service type, timeout/retry, missing times and navigation after success. **Done:** no duplicate plan or false success on network failure; shared/backend/native checks pass.

## Pass B — Templates and multiple dates

4. Reuse F10's saved templates, revisioned preview and atomic/resumable batch contract. If absent, implement that Services pass before adding controls. Add bounded date selection with per-date adjustment and actual template choice. **Done:** the preview lists every resulting date/time/item/need and identifies stale or incompatible template data.
5. Confirm append/replace/apply intent and review conflicts, copied roster scope and preparation state. Copies reset answers, notification timestamps and actual timing; existing destination answers change only through an explicit supported reset policy. Submit one idempotent server operation. **Done:** rollback leaves no partial batch, or an explicitly resumable batch exposes per-plan persisted results and safe retry.
6. Show created plans and any tracked failures, refresh scoped queries and retain provenance. Template edits affect future copies only. Test DST weekly generation, duplicate retry, removed template, stale revision, mid-batch failure and unauthorized date/service type. **Done:** native matches the canonical web preview/commit semantics.

**Acceptance:** the single-plan pass can ship independently; full template/batch acceptance requires persisted F10 behavior. No copied confirmations, implicit publication notifications or browser-style creation loop presented as atomic.

**Handoff:** completed pass, template/batch prerequisites, generated-plan evidence and remaining device gates. Existing plan duplication remains distinct from reference native parity.
