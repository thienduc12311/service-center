# MOB-031 — Scoped directory, own profile and team editing

Read [execution rules](../IMPLEMENTATION-RULES.md). **User story:** As a leader, I find permitted people/contact/team information; as a volunteer, I update my own profile without exposing another person's sensitive data.

**Read:** mobile spec directory section; US-01.1/02.3; [F01](../services-capabilities/F01.md), [F02](../services-capabilities/F02.md) and F13 avatar lifecycle; native profile/AuthProvider; website PeoplePage, PersonPage, TeamsPage; backend people/team/me routes and shared Person/membership schemas.

## Pass A — Directory and self profile

1. Inventory field-level permissions and mixed Profile/Person roster IDs. Define minimal directory summary/detail projections; medical/private fields must not arrive and then merely be hidden on-device. **Done:** API and RLS/data-projection tests deny restricted fields and foreign-organizational Person links.
2. Add bounded searchable People list/detail with permitted contact actions, teams/positions and linked/no-login state. Avoid a full private roster download. Gate every contact link and handle missing/redacted fields distinctly. **Done:** scoped leaders and ordinary members receive appropriate projections and denied detail links fail safely.
3. Extend own profile photo/contact editing using verified picker permissions, F13-style authorized upload/finalize and validated me/Person mapping. Never allow an arbitrary target ID to turn a self endpoint into an admin update. **Done:** edited data reloads correctly and failed upload creates no false profile success or orphaned ready file.

## Pass B — Authorized membership/tags/lifecycle

4. Add permitted team/position membership changes using canonical Person identity, same-org checks, revision/audit and explicit consequences for scheduled history. Implement/reuse F02 tags/archive before exposing tag/bulk or archive controls. **Done:** membership edits do not delete past assignments or grant scheduling authority by themselves.
5. Keep permanent deletion out of the default action menu; use reversible archive where implemented. Native new-person onboarding is an optional later flow, not assumed parity. **Done:** visible actions have actual APIs and safe history behavior.
6. Test private search snippets, unauthorized person/membership mutation, no-login detail, image permission denial, failed photo finalize, org switch and archived history. Run common checks and native contact/picker/device review. **Done:** bytes, fields, action scope and audit agree across web/native.

**Acceptance:** minimal authorized directory, working self edits, scoped team/tag actions and preserved history. A Person record never implies permission to see their private fields.

**Handoff:** projections/capabilities, identity mapping, supported edit stages and pending image/device gates.
